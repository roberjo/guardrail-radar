    • Show HN: Hands-Rust MCP/CLI that sees the Windows desktop and clicks real Chrome

      Notable1 min read

      Lets an agent click and type on a real desktop convincingly enough to dodge most automation detection.

      Read the source excerpt
      I built Hands because I wanted a coding agent to use this Windows PC and a real Chrome profile the way I do: look at the screen, move the real mouse, type, click , without turning Chrome into an automation browser. It is a Rust MCP/CLI. A harness (Grok, Codex, Claude Code, OpenCode, etc.) calls tools like observe, click, type, scroll. Observe is a screenshot path plus a small element list (UIA + optional Chrome DOM ids). Click is OS SendInput on a Bézier path, not a Chrome DevTools click. There is no Playwright, no Puppeteer, no remote debugging port. Daily Chrome is launched with no extra flags, or attached if it’s already open. Sites that key on CDP/automation flags mostly don’t see that. They can still see injected input (LLMHF_INJECTED). A tiny unpacked Chrome extension can fuse page structure (chr: ids, listing cards) so the model isn’t guessing from pixels. Sideload is manual. Fusion dies if the service worker goes inactive; reload the card. What it is good for:

      Hands is a Rust MCP/CLI that lets a coding-agent harness (Grok, Codex, Claude Code, OpenCode, etc.) drive a real Chrome profile via actual OS-level input — not Playwright, Puppeteer, or a remote debugging port — specifically so sites that key off CDP/automation flags mostly don't detect it as automated. Genuinely useful for legitimate testing, and also a direct description of how to make agent-driven browser activity indistinguishable from a human's to any system trying to tell the difference. Worth knowing this class of tool exists before assuming your bot-detection or session-monitoring controls would catch an unsanctioned agent using one.

    • Coding Agents killed my identity. How do you feel?

      Field Notes1 min read

      One senior engineer's unfiltered account of what full agent delegation actually feels like.

      Read the source excerpt
      Programming is like a game of chess for me: winning (i.e. delivering a product) is important, but only if I played this game myself. I don't enjoy winning if my opponent disconnected. I don't enjoy beating people who don't know how to move pieces. I don't enjoy winning with an engine, and coding agents are basically "winning with a chess engine". I started to use AI for coding a long time ago, when copilot was first introduced. At first, I was happy: "wow, this can write boring boilerplate and unit tests". Time went by, agents got better, time spent writing code myself went down. Half a year ago I suddenly realized I hadn't written any code for over a month, and I am a full-time software dev without any managing work. Not only did I stop writing code, but agents also became pretty good at proposing plans and architectures, and I was mostly providing missing context and technical details of our infrastructure. One day the realization hit hard. Coding agents removed everything I loved, a

      A full-time software engineer writes on HN that they realized they hadn't personally written code in over a month — not from moving into management, but because agents had gradually taken over first the boilerplate, then the planning and architecture, leaving them mostly supplying context and infrastructure details. Framed as "winning with a chess engine": still shipping, but with the part of the job they valued removed. Worth surfacing for any engineering lead rolling out agent adoption — retention and job-satisfaction risk is a real cost that a pure productivity metric won't show.

    • FetchSandbox MCP

      New Product1 min read

      Proves an AI agent's fix actually held, not just that it passed CI.

      Read the source excerpt
      The MCP that proves your AI's integration fixes work — Your agent's integration fix passes CI. The data is still wrong. FetchSandbox MCP reproduces the real failure on your code, fixes it, and proves the fix held. A receipt, not a vibe. 70+ API sandboxes. One config block in Cursor or Claude Code.

      FetchSandbox MCP targets a specific failure mode this audience will recognize: an agent's fix passes CI while the underlying data or integration behavior is still wrong. It reproduces the real failure against one of 70+ API sandboxes and re-verifies the fix actually held, rather than trusting a green test run — positioned explicitly as "a receipt, not a vibe." For a team that has to show its work on why an AI-assisted change was safe to ship, that's the right instinct, though the excerpt doesn't say what the receipt actually contains or where it's stored for later audit.
